## 2026-11-10 / 2026-11-17: v1 モデル、5 エポック（Claude 導入前）

- v1 構造（128×128 で attention）、fp32、DDPM 1000 ステップでの生成。
- **ラベルのバグ**（commit `ac23bbd` で修正）があり、cat も bedroom（ラベル 0）として学習されていた。結果は使えない。
- 時間: 1 エポック約 63 分。FID 評価（約 100 枚）に約 42 時間（11/17 20:50 → 11/19 15:02 JST）。

## 2026-11-24: v2、600 エポック（最初の長い学習）

- **設定:** v2、バッチ 16、lr 1e-4（ウォームアップ 1000 + コサイン）、bf16、EMA 0.9995、CFG 3.0、`lambda_=0`、SORT=False、左右反転なし。
- **結果:** FID = **144.2**（EMA、2000 枚、DPM-Solver++ 50 ステップ）。
- **時間:** 学習 35時間54分（見積もり約 22 時間）、最終 FID 5.5 時間（見積もり 2.6 時間）。
  - 原因はたぶん **同じ GPU での別の学習との競合**（ユーザーの判断）。学習中の 11/25 03:16 JST に、別のコンテナ `yuka-var` で tmux セッション `wm0b` が始まっていた。
  - 「SW Power Capping」（電力制限）の累計が約 69 時間あった（11/10 の起動から）。
- **画像の印象**（`samples/`）:
  | エポック | bedroom | cat |
  |---|---|---|
  | 200 | ぼやけていて、ベッドの形がなんとかわかる | ほぼ色のかたまり |
  | 400 | 形がはっきりし、窓や家具も出てくる | 8枚中3〜4枚は猫とわかる |
  | 600 | 細部は増えたが、ざらざら・しわしわの質感 | 400 よりはっきり良いとは言えない |
  - どのエポックでも色が強く偏っている（全体がピンク、全体が青など）→ CFG 3.0 が大きすぎる可能性 ❓
- **考察:**
  - loss は 20 エポックほどで下がりきり、その後はほぼ平ら（loss では画質の変化は見えない）。
  - 過学習（丸暗記）の心配: ユーザーが画像を見て、学習画像ほど画質の良いものはないので**丸暗記はない**と判断。
  - 主な制約はデータの少なさ（各クラス 500 枚）。特に cat は姿勢・背景がばらばらで難しい。
  - → 次の実験で**左右反転のデータ拡張**を入れる。

- 11/27 15:51 JST に SSH が切れて比較用のループは止まったが、cfg 3.0 の評価は最後まで終わった（2.35 s/it で一定、他の学習との競合なし）。

## 次の予定: 左右反転あり、600 エポック

- `python3 LSUNtrain.py --epochs 600 --cfg <CFG 比較で一番良い値> --wandb --save-dir content/runs/2026-11-27_hflip`
- 前回（2026-11-24）との違いは**左右反転だけ**（バッチ 16 のまま）。
- CFG 4.0・5.0 の評価が終わったらすぐ始める（ユーザーの指示）。始める前に、GPU を他の処理が使っていないか確認する。tmux の中で起動する。
- 5.0 でもまだ FID が下がっていたら、さらに上の値を試すかユーザーに相談する。

## その後の予定: 測定（学習の後、または学習中）

- **v2、バッチ 16 と 32 の 1 ステップの時間とメモリ**（本番と同じ bf16 + EMA）。時間は GPU が単独のときに測る → 学習が終わってから。
  バッチ 16 の時間は、学習の wandb のエポック時間からもわかる。
- **v1 の 1 ステップのメモリ**（当時と同じ fp32、EMA なし）。以前「学習のゲージが全く進まずに固まった」原因の確認。
  `--max-mem-gb` で上限をかけて安全に測る。メモリは取り合いの影響を受けないので、学習中でも測れる（上限は低めにする）。
